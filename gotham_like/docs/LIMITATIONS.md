# Known limitations, technical debt, bottlenecks, risks, next steps

## Known limitations

* **Single-tenant**: no organisation / compartment separation. Investigation-level write control exists
  (owner, collaborators, INVESTIGATOR/ADMIN), but every authenticated user can *read* all investigations and entities.
  Classification-based compartments (need-to-know) are not implemented.
* **Entity resolution** is pairwise, rule-weighted and deterministic. There is no transitive-closure review UI, no
  clerical-review queue beyond POSSIBLE_MATCH candidates, and weights are global (not per source). Unmerge must
  proceed newest-first for a canonical entity.
* **Time semantics**: relationships carry a single `timestamp` plus optional `start_time`/`end_time`; graph time filters use
  `timestamp` only (validity intervals are not yet queried). Edges without timestamps always pass time filters.
* **Path finding** runs exact algorithms on a *bounded window* built by fan-out-capped bidirectional expansion; with
  high-degree hubs the window can be truncated, in which case the result says so (absence of a path is then not evidence).
* **Graph analytics** run in-process with NetworkX on windows (default ≤ 10k nodes). Whole-graph analytics
  (global PageRank over 10M edges) are out of scope for the online API.
* **Search** is lexical (trigram + identifiers). There is no phonetic matching, transliteration, or synonym support.
* **Map** ships an offline graticule basemap (no coastlines/streets). Real basemaps need a self-hosted tile server
  (`VITE_MAP_STYLE_URL`).
* **Rules** are deterministic templates (8 kinds). There is no general rule DSL editor in the UI (rules are JSON / API).
* **Reports** are generated synchronously; very large investigations (thousands of pinned entities) will be slow.
* **Uploads** are stored on local disk (content-addressed), not in object storage, and are not malware-scanned.
* **Frontend** state is in-memory per tab; graph workspaces are persisted only by pinning into investigations.

## Technical debt

* Request models live next to routers; there are no explicit `response_model`s, so OpenAPI response schemas are generic.
* The query builder compiles patterns to SQL joins; patterns with many edges produce wide joins without cost-based
  reordering beyond PostgreSQL's planner. Variable-length path patterns are not supported (use `/api/graph/path`).
* Ingestion is synchronous (called from scripts / services); there is no job queue, scheduler or connector UI.
  Long-running work reports progress over the WebSocket only for rule evaluation.
* Rule evaluation re-scans the relevant relationship sets; there is no incremental (delta) evaluation.
* ER merges copy identifiers but do not re-point `signals` / `investigation_items` that reference merged ids (the API
  resolves ids through `merged_into` at read time instead).
* Some UI views fetch data per interaction without request cancellation or client caching.
* Alembic migration `0001` is autogenerated; later schema changes should be hand-reviewed migrations.

## Performance bottlenecks

* **Hub nodes**: ranking a hub's edges for the fan-out cap reads its whole index range (see `EXPLAIN` in
  BENCHMARKS.md). Mitigations: pre-computed degree table + "top-k recent edges" materialisation, or per-type fan-out.
* **Exact betweenness** on windows > ~1,500 nodes (switches to sampling), and Louvain on large windows.
* **Timeline histograms** over very wide windows without entity filters aggregate many rows; a time-bucketed
  materialised view (or TimescaleDB continuous aggregates) would help.
* **Trigram search** degrades for very short terms (< 3 characters) and very common tokens.
* **Bulk ingestion through the pipeline** maps records in Python (≈550 transaction records/s on the demo set, each producing 5 entity upserts, 4 edges, 1 event and lineage rows);
  large backfills should use COPY-based loaders with index rebuilds (as the benchmark does).
* **Audit hash chain** serialises writers via an advisory lock (one audit row per request); at very high write rates
  this becomes a contention point — batch or partition the chain.

## Security risks

* Demo users with a shared default password exist after `seed_demo.py`; never run it in production.
* Bearer tokens in `sessionStorage` are exposed to any XSS; CSP mitigates, but an `HttpOnly` cookie session behind
  the same origin is stronger.
* No MFA / SSO integration (expected to be provided by a reverse proxy / IdP in production).
* Existence disclosure via fuzzy search for VIEWER (masked labels still reveal that a record matches).
* The PostgreSQL role used in development is a superuser (needed for extensions in tests); production must use a
  least-privilege role and a separate owner for the audit trigger.
* Rate limiting is per IP; distributed attacks need an upstream WAF.
* Uploaded files are not scanned for malware.

## Recommended next implementation steps

1. Compartments / classification labels on sources, entities and investigations with need-to-know enforcement.
2. Job queue (e.g. Redis streams / arq) for ingestion, ER, rule evaluation and report generation, with WebSocket progress.
3. Degree/`top-k` edge materialisation for hub nodes; time-bucketed aggregates for timelines.
4. Validity-interval (bitemporal) relationships and "as-of" queries.
5. ER clerical-review workspace (side-by-side record comparison, cluster view, per-source weights).
6. OIDC/SAML login and MFA; `HttpOnly` cookie sessions; per-user API tokens with scopes.
7. Connector management UI with schema inference and mapping editor; scheduled incremental ingestion.
8. Optional analytical assistant as an **API client** (no core coupling): drafts queries and summaries whose outputs are
   stored as `SYSTEM_INFERENCE`, always with citations to provenance ids.
9. Object storage for documents with malware scanning; document entity extraction as a separate, auditable pipeline.
10. Load testing of the HTTP layer (k6/Locust) and PostgreSQL tuning guide (shared_buffers, work_mem, partitioning of
    `relationships` / `events` by time for > 100M rows).
